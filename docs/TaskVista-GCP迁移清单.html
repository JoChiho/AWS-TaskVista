TaskVista Google Cloud 迁移清单

将现有 AWS Serverless 应用迁移为 GCP 无服务器架构的实施、验证与上线清单。

项目： AWS-TaskVista建议区域： asia-northeast1（东京）推荐架构： Cloud Run + Cloud SQL

目标架构

浏览器 ── Firebase Hosting（Vue 3 SPA / CDN）
  ├── Identity Platform（登录与 JWT）
  └── Cloud Run（TaskVista HTTP API）
        ├── Cloud SQL for PostgreSQL（业务数据）
        ├── Cloud Storage（任务附件）
        └── Logging / Monitoring / Secret Manager

前端后端认证数据 选择 Cloud SQL 的原因是项目、成员、任务、评论和 WBS 层级存在强关联，且看板筛选与 Dashboard 汇总更适合 SQL 查询。

1. 迁移前确认

  • 确认 GCP Organization、Billing Account 与项目，例如 taskvista-prod。
  • 确认域名：app.example.com 与 api.example.com。
  • 备份 DynamoDB 的 Projects、Tasks、Comments、Users 表；备份 S3 的附件 bucket。
  • 确定数据冻结、停机或双写窗口，防止两端数据分叉。
  • 确认 Cognito 用户迁移策略：重设密码，或短期以 OIDC 联邦方式保留 Cognito。
重要：Cognito 密码通常不可导出。因此必须在正式迁移前明确首次登录重设密码或临时联邦登录方案，并保留旧用户 ID 的映射表。

2. 创建 GCP 资源

  • 启用 Cloud Run、Cloud SQL Admin、Cloud Storage、Artifact Registry、Cloud Build、Secret Manager、Identity Platform、Cloud Logging 与 Monitoring API。
  • 创建 Artifact Registry 仓库，用于保存 API 容器镜像。
  • 创建 Cloud Run 服务：taskvista-api。
  • 创建 Cloud SQL PostgreSQL 实例和数据库：taskvista。
  • 创建私有 Cloud Storage bucket：taskvista-attachments-<project-id>。
  • 创建 Firebase 项目并启用 Firebase Hosting。
  • 启用 Identity Platform，配置邮箱密码、Google 登录或所需企业 SSO。
  • 在 Secret Manager 中保存数据库连接信息及其他机密。
  • 为 Cloud Run 创建专用服务账号，并最小化授予 Cloud SQL、Storage 与 Secret Manager 权限。

3. AWS 到 GCP 服务映射

AWSGCPTaskVista 用途
Lambda + API GatewayCloud Run项目、任务、评论、附件、Dashboard API
DynamoDBCloud SQL for PostgreSQL关系数据、筛选、WBS 与聚合查询
S3Cloud Storage附件、交付物和临时访问 URL

CloudFront + S3Firebase HostingVue SPA、CDN、HTTPS 与自定义域名
CloudWatchCloud Logging / Monitoring日志、指标、告警和错误跟踪

4. 数据建模与数据迁移

现有来源PostgreSQL 目标关键项
TaskVista-Projectsprojects, project_members项目—成员多对多
TaskVista-Taskstasks, task_assignees, task_reviewers, task_attachmentsproject_id、parent_task_id、wbs_code、状态索引
TaskVista-Commentscomments(task_id, created_at) 索引
TaskVista-Usersusersidentity_provider_uid、email 唯一约束
S3 对象Cloud Storage 对象保留 tasks/{taskId}/... 路径
  • 创建 SQL migration：表、外键、软删除字段、索引及 (project_id, wbs_code) 唯一约束。
  • 导出 DynamoDB；按 Users → Projects → Members → Tasks → Comments → Attachments metadata 顺序导入。
  • 复制 S3 附件到 Cloud Storage，并核对每个元数据对象实际存在。
  • 核对记录数、每项目任务数、WBS 父子关系、排序、评论作者和成员关联。

5. 后端代码改造

  • 将 backend/src/shared/dynamodb.ts 改为 PostgreSQL 连接模块。
  • 将 projects、tasks、comments、users Repository 中的 DynamoDB Command 改为 SQL 查询。
  • 将 attachments/repository.ts 的 S3 SDK 改为 @google-cloud/storage。
  • 保留预签名 URL 行为：上传 15 分钟、下载 60 分钟；维持 50MB 限制、MIME 校验及项目访问控制。
  • 将 shared/cognito.ts 的用户查找改为查询 users 表。
  • 新增 Identity Platform JWT 校验中间件，并保持 Authorization: Bearer <token> API 合约。
  • 将现有 5 个 Lambda handler 合并为一个 Cloud Run HTTP 服务；保留现有 REST 路径和响应格式。
  • 使用 Secret Manager 注入机密，增加 /healthz 健康检查与 PostgreSQL integration test。

6. 前端认证与发布改造

  • 在 Identity Platform 配置生产与本地回调 URL。
  • 用 Firebase / Identity Platform Web SDK 改造 frontend/src/stores/auth.ts。
  • 移除 Cognito 授权 URL、token 端点和相关环境变量。
  • 将用户 sub 映射到 identity_provider_uid，保证历史成员、负责人、评论作者能对应。
  • 更新 VITE_API_BASE_URL 和 Firebase 前端配置。
  • 发布至 Firebase Hosting，设置 SPA rewrite、自定义域名、CORS 及 HTTPS。

7. IaC、CI/CD 与生产保护

  • 新建 infra/gcp/，以 Terraform 管理 Cloud Run、Cloud SQL、Storage、IAM、Secret 与告警。
  • 新增 cloudbuild.yaml：前后端测试 → 构建镜像 → 推送 Artifact Registry → 部署 Cloud Run → 发布 Hosting。
  • 分离 dev、staging、prod 项目或资源配置。
  • Cloud SQL 启用自动备份、PITR；生产环境启用高可用。
  • Cloud Storage 启用软删除／版本控制及生命周期规则。
  • 配置错误率、延迟、5xx、数据库连接数和附件失败告警。
  • 生产 API 接入 Cloud Armor 的 WAF 与限流策略。

8. 上线验收与切换

  • 在 staging 完成登录、项目／成员、任务 CRUD、WBS 重排、看板、时间线、评论、附件和 Dashboard 验收。
  • 验证未授权用户不能读取项目、任务或附件。
  • 执行数据库备份和恢复演练。
  • 生产发布使用 Cloud Run revision 灰度流量；观察日志、错误率和用户反馈后全量切换。
  • 确认 GCP 数据无误并完成回退窗口后，再下线 AWS 资源与访问密钥。

推荐顺序：基础设施与数据库 → 后端改造与测试 → 数据／附件迁移 → 身份认证与前端 → staging 验收 → 生产灰度切换。
